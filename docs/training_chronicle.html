Hot-Swap Zero-Downtime Resubmit — Keeping GLM-5.2 Continuously Available (Jun 25, 2026)

GLM-5.2 is the best coding model we serve (~220-250 tok/s, 754B MoE, 40B active, 1M ctx, Terminal-Bench 81%) — but its 3-day Slurm wall-time means it lapses every 3 days. A naive "let it expire then resubmit" causes a 15-minute outage mid-work while DeepGEMM JIT-compiles 16K kernel variants from scratch. For a model that is the primary coding backend for daily Claude Code sessions, that downtime is unacceptable.

The fix is a rolling resubmit — same model, fresh instance, zero serving gap. Both instances briefly coexist on different nodes; ~15 min of double GPU allocation is acceptable given idle fat nodes available. This is NOT a model swap. It preserves the best model by booting a fresh copy before killing the aging one.

StepActionDetail
1Find idle fat node8× B200 free via sinfo -p fat -N
2Submit fresh instance--qos=3d (expensive boot → 3d, not 1d)
3Verify healthyProbe /v1/models + confirm throughput after ~15-min cold boot
4Kill OLDER jobBy least wall-time runway remaining — NOT by QoS number
5Switch tunnelPoint SSH tunnel + proxy to new node. Zero serving gap.

QoS correction. Slurm QoS ("Quality of Service") is a priority tier + wall-time ceiling, not a performance setting. The old rule "always use --qos=1d for serving" was wrong — it forces daily resubmits on models that take 15 minutes to boot. The correct rule is QoS by reload cost:

Boot CostQoSExamples
Expensive (~15 min)--qos=3dGLM-5.2 (DeepGEMM JIT), MiniMax M3 (Triton JIT)
Cheap (~1-2 min)--qos=1dGemma-4 (native Transformers), Qwen3 (SGLang pip)
Training--qos=7dSFT/GRPO/DPO jobs (long runs, resubmit cheap)

Concrete instance: Current GLM-5.2 job expires 2026-06-27 09:45. Hot-swap planned for 2026-06-26 — submit fresh instance on a different node, wait ~15 min for DeepGEMM cold boot, verify /v1/models returns serving at expected throughput, then scancel the older job. ~15 min of double 8× B200 allocation is a trivial cost vs. a 15-min outage on the primary coding model.

Critical Fix: DeepSeek Tool Call Parser

DeepSeek-V4 uses a custom "DSML" markup language for tool calls instead of standard JSON function calls. Without a parser, SGLang returns raw DSML text, breaking Claude Code's tool use entirely.

Before (broken)
<｜DSML｜tool_calls> <｜DSML｜invoke name="read_file"> <｜DSML｜parameter name="path"> /tmp/test.txt </｜DSML｜invoke>
After (working)
{ "tool_calls": [{ "function": { "name": "read_file", "arguments": "{\"path\": \"/tmp/test.txt\"}" } }] }

Critical Fix: Proxy Corrupts Tool History → Model Mimics Text

After multi-turn tool usage, Claude Code's agents would describe tool calls in text instead of executing them. The output looked perfectly formatted — [Tool: Agent (ID: call_xxx)] Input: {...} — but nothing executed.

Root Cause
// Proxy's OpenAI conversion flattened // tool_use blocks to TEXT in history: elif block.type == "tool_use": text += f"[Tool: {name} (ID: {id})]" text += f"\nInput: {json}\n" // V4-Flash saw this pattern in history // and MIMICKED it instead of using DSML
Fix: Proper OpenAI Format
// Assistant messages → tool_calls array {"role": "assistant", "tool_calls": [{ "type": "function", "function": {"name": "...", "arguments": "{}"} }]} // Tool results → role: "tool" {"role": "tool", "tool_call_id": "call_xxx", "content": "result"}

⚠ Key Insight: The model's conversation history IS its few-shot context. Corrupt tool structure → model outputs tools as text. This is undocumented in any proxy/LiteLLM repo.

Smart Context Compression & Thinking History Fix (2026-06-02)

Two critical proxy improvements that fix conversation coherence for long Claude Code sessions. Models no longer lose context mid-conversation or get confused by their own thinking history.

Tiered Compression (replaces FIFO)
Tier 1: Truncate tool_result (500 chars) Tier 2: Strip tool_use, keep text (2K) Tier 3: Truncate user messages (1K) Tier 4: Drop pairs → session memory Last 8 msgs ALWAYS protected. Session facts injected into system msg.
Thinking History Stripped
Problem: THINKING_MODE=text prepends thinking as text in response. On next turn, model re-sees own thinking → confusion + token waste. Fix: regex strips all thinking blocks from assistant msgs before forwarding. Model only sees actual responses.

GLM-5.1: Tool Calling & Per-Request Thinking Control

GLM-5.1 generates tool calls as custom XML and wraps all responses in <think>...</think> tags by default. Both leaked raw into Claude Code and Zed until properly configured.

Problems (3 issues)
1. Tool calls as raw XML in content: <tool_call>get_weather <arg_key>city</arg_key> <arg_value>Munich</arg_value> </tool_call> 2. <think> tags leaking into responses 3. No per-request thinking control
Solution (SGLang parsers + proxy)
--tool-call-parser glm47 → XML → structured tool_calls[] --reasoning-parser glm45 → <think> → reasoning_content field reasoning_effort: "none" | "high" → per-request thinking toggle
glm47
Tool Parser (5.x XML format)
glm45
Reasoning Parser (<think> tags)
/effort
Claude Code slider → SGLang

Key insight: glm45 vs glm47 tool parsers detect different XML layouts. GLM-4.5/4.6 uses newlines between <arg_key> tags; GLM-5.x uses inline. Both share the same <think> wrapper, so reasoning parser is glm45 for both. Parsers are output post-processors only — zero quality impact.

🎯 Thinking control: Claude Code's /effort slider maps to SGLang's reasoning_effort via proxy. Zed gets thinking ON by default (GLM's native behavior) with clean separation via reasoning_content field.

Proxy: Anthropic Thinking ↔ SGLang reasoning_effort

// Claude Code /effort slider

thinking.enabled = false →  reasoning_effort: "none"  →  No thinking, fast response

// Zed (direct to SGLang, no proxy)

MiniMax M3 MXFP8 on 4× B200 — the symmetric_memory.rendezvous deadlock 2026-07-12

Symptom

7 jobs deadlocked at NCCL init · GPU 1.1GB / 0% util · log frozen

MiniMax M3 MXFP8 (427B MoE / 26B active, multimodal) would not boot on 4× B200. Workers reached world_size=4 backend=nccl then froze. A prior boot (2026-06-22, job 2190313, same container/args) had succeeded in 33s — so the config was supported, the deadlock was non-deterministic.

strace -c: ~350K ioctl+sched_yield/sec · R-state · wchan=0 · pure userspace spin

Root cause (py-spy)

Model-layer call to fused all-reduce+RMSNorm

rendezvous  (torch/_symmetric_memory/__init__.py:1991)
  ← trtllm_create_ipc_workspace_for_all_reduce_fusion
  ← flashinfer_all_reduce._create_workspace
  ← get_fi_ar_workspace
  ← _can_use_flashinfer  (fused_allreduce_gemma_rms_norm.py:90)
  ← fused_allreduce_gemma_rms_norm.forward
  ← minimax_m3/nvidia/model.py:760  (direct model-layer call)

MiniMax's model calls the fused op directly in forward() — bypassing every config flag (-O 1, --enforce-eager, VLLM_ALLREDUCE_USE_*). vLLM issue #45800 reports the same hang (open/unresolved).

The fix — bind-mounted source patch

Two vLLM source files patched & bound over the container's copies

FilePatchEffect
fused_allreduce_gemma_rms_norm.py _can_use_flashinfer() → (False, 0) Model takes fallback: all_reduce + GemmaRMSNorm (numerically identical, per vLLM docstring)
flashinfer_all_reduce.py get_fi_ar_workspace() → None Belt-and-suspenders: any caller skips _create_workspace → rendezvous

Patched files: /shared/project//llm/tmp/vllm-patch/vllm/{...} · wired in serving/serve-minimax-m3-container.sh. With the patch: boot reaches cuda_communicator.py:245 Using ['CUSTOM','PYNCCL'], loads weights in ~30s, compiles CUTLASS MSA kernels for SM100 (cold-cache AOT ~3min), then serves.

Result — healthy

4× B200 · TP=4+EP · port 8105 · 811K ctx · vision+video

  • /health 200 OK · GPU mem 150GB · util 73–99% under load
  • Text + image (image_url) inference verified
  • claude-minimax e2e: claude → :5032 (logger) → :5014 (proxy) → :8105 (tunnel) → MiniMax
  • Tool calls work (Bash tool ran echo MINIMAX_E2E_OK) · per-request <mm:think> works

Why 2× B200 was impossible

Three independent walls — not a config issue

PathBlocker
NVFP4 (233GB, fits 2×)TP=2 deadlocks in MSA rendezvous · vLLM recipe tests TP=8 only
MXFP8/FP8 (414GB)207GB/GPU > 192GB · OOM
Pipeline parallel (PP=2)NotImplementedError — MiniMax M3 lacks SupportsPP

Lessons

  1. Research upstream before the 2nd failing boot. 7 jobs re-derived what the vLLM recipe + issue #45800 said in one fetch.
  2. strace -c + py-spy dump are decisive for "stuck process" — ps can't tell real work from spin. strace syscall-count + py-spy stack found the call site in minutes.
  3. The Blackwell cold-boot wedge is a family. GLM-5.2 (SGLang, FlashInfer autotune) & MiniMax M3 (vLLM, symmetric_memory.rendezvous) — same B200/SM100 cold-cache deadlock class.
  4. Read the source for the real env-var name. vLLM naming is inconsistent (_BACKEND vs _USE_FLASHINFER vs _USE_SYMM_MEM); issue #45800's reporter tried the wrong name and gave up.
  5. When flags don't gate the buggy path, patch the source. Every config flag targets paths the MiniMax model doesn't use — it calls the fused op directly in forward(). A bind-mounted source patch is the surgical fix.

The breakthrough

DSpark is DeepSeek's native speculation algorithm (arXiv 2606.19348, PR #30261 in SGLang, released July 2026 in v0.5.16). It uses layers 40-42 of the same checkpoint as the drafter — no separate draft model, no extra VRAM. The hard requirement: SGLang 0.5.16+ (sglang-v0516.sif).

Our sglang-latest.sif was SGLang 0.5.13.post1, which hard-asserts EAGLE only for DeepSeekV4 via the apply_deepseek_v4_defaults hook. DSpark/DFLASH are rejected.

The mistake I made: When DSpark failed on 0.5.13.post1, I gave up on it and spent 6 boot cycles tuning EAGLE — none exceeded 119 tok/s. The user said "Why didn't we do DSpark yet?" — and the fix was simply to pull a newer SGLang container. DSpark worked immediately, hit 256 tok/s. Lesson saved to feedback_dspark_not_eagle.md.

Final config

  • Container: sglang-v0516.sif (SGLang 0.5.16-cu130 from lmsysorg/sglang:v0.5.16-cu130)
  • TP=4, flashinfer_mxfp4 MoE backend, dsv4 attention
  • --speculative-algorithm DSPARK --speculative-dspark-block-size 5 (gamma=5)
  • --enable-deepseek-v4-fp4-indexer
  • --cuda-graph-max-bs 192 (lmsys blog value)
  • --mem-fraction-static 0.90, --kv-cache-dtype fp8_e4m3
  • --chunked-prefill-size 4096, --disable-flashinfer-autotune
  • FlashInfer + Triton caches on disk (not tmpfs — host RAM OOMs during JIT)

Known issues to watch

  • PR #33614 (OPEN): DSpark TP rank divergence — sampling decisions made independently per rank, may deadlock at TP>1 (we're TP=4). Watch for deadlocks at long context.
  • Issue #33549: decode hang at ~245K context with DSpark + TP=8. TP=4 less affected, but watch past 200K.
  • Issue #33493: DSpark looks up acc_linear_penalities (typo) instead of acc_additive_penalties. Breaks min_new_tokens and additive penalties.
